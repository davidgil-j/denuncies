<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| ComplaintForm/App (caller) -> saveComplaint organizationId param | organizationId must originate only from a fresh slug resolution, never from form state — enforced by convention here (the function reads it solely from the param), and by plan 03-03's wiring |
| getComplaintByCode -> get_complaint_by_tracking_code RPC | trackingCode and organizationId passed as parameterized rpc() args; org filtering happens server-side (migration 007), so a forgotten client-side check cannot leak cross-tenant rows |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-06 | Tampering / Elevation of Privilege | saveComplaint organization_id sourced from user-editable form data | mitigate | organization_id is read ONLY from the `organizationId` param, never `formData`; acceptance criteria assert the insert key is `organization_id: organizationId`; the FK constraint + non-null RLS check (migration 005) further constrain it to a real org (Pitfall 1) |
| T-03-07 | Information Disclosure | getComplaintByCode leaking a cross-tenant complaint | mitigate | Switched to the 2-arg RPC which filters by organization_id server-side; client cannot retrieve a mismatched-org row even if it passed a wrong code (PUBLIC-03) |
| T-03-08 | Information Disclosure | direct organizations table query exposing all org names/slugs | mitigate | No `supabase.from('organizations')` added; resolution goes only through the minimal-return-shape `get_organization_by_slug` RPC (acceptance criteria assert zero direct org-table queries) |
| T-03-05 | Tampering | SQL injection via slug/code/org id | accept | All values pass through Supabase `rpc()` parameterized calls, never concatenated SQL (ASVS V5) |
</threat_model>
